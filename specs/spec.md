# FreePlot 项目规整与文档建设需求

## 目标

将 `freeplot` 规整为类似 `freerec` 的现代 Python 项目, 建立清晰的工程结构、构建配置、文档体系、文档示例和基础验证能力, 使项目更易安装、使用、维护和后续发布。

## 背景

当前 `freeplot` 已具备核心包代码、README、示例脚本和图片资源, 但工程配置仍以旧式 `setup.py` 为主, 文档体系较弱, 示例目录存在重复, 测试与开发规范不足。后续不再维护独立 demo 目录作为主要学习入口, 示例应沉淀到 `docs/` 文档中。

参考项目 `freerec` 已具备较完整的现代 Python 项目形态, 包括:

- `pyproject.toml` 构建配置
- `docs/` Sphinx 文档目录
- `tests/` 测试目录
- README 信息架构
- Ruff、pytest、pre-commit 等开发配置
- 文档示例与 API 文档组织方式

本需求中的“模仿 freerec”指参考其项目规整方式和文档组织方式, 而不是照搬其推荐系统领域功能。

代码风格规整应引入 `format-code-style` skill 作为个人代码风格参考, 用于指导后续代码生成、编辑、审查、格式化、类型标注、注释和测试组织。

## 范围

### 包与构建配置

- 新增或迁移到 `pyproject.toml`, 明确项目元数据、依赖、可选依赖和构建后端。
- 保留或兼容现有 `setup.py`, 降低迁移风险。
- 明确 Python 版本要求、运行依赖和开发依赖。
- 保证本地可通过 editable install 安装项目。

### 项目结构

- 梳理根目录文件, 使项目入口、配置、文档、示例和测试职责清晰。
- 处理 `demos/` 与 `freeplot/demos/` 的重复关系, 不再将独立 demo 目录作为目标交付物。
- 保持 `freeplot/` 作为核心包目录, 不在本阶段重写公共 API。

### 文档体系

- 建立 `docs/` 文档目录, 参考 `freerec` 的 Sphinx 文档结构。
- 至少包含安装指南、快速开始、示例索引和 API 参考入口。
- 将常见绘图示例写入 `docs/`, 使文档成为主要示例入口。
- README 与文档内容保持一致, README 侧重快速理解和快速上手。
- 保留现有图片资源, 并按文档需要整理引用路径。

### 文档示例

- 在 `docs/` 中整理折线图、柱状图、散点图、热力图、雷达图、小提琴图、局部放大图和 3D 曲面图示例。
- 示例应能作为用户学习入口, 代码片段、说明和输出图引用应统一。
- 文档示例代码应尽量支持无 GUI 环境运行, 避免阻塞自动化验证。

### 测试与验证

- 增加最小测试集合, 覆盖包导入、核心模块可访问性和关键文档示例可运行性。
- 配置 pytest, 使项目具备基础回归验证能力。
- 配置 Ruff 或同类工具, 提供基础代码风格检查。
- 文档应能本地构建, 至少验证 Sphinx 配置和主要页面无明显错误。

### 代码风格规整

- 使用 `/Users/mtandhj/Desktop/freeskill/skills/format-code-style/SKILL.md` 作为代码风格规整参考。
- 非平凡代码生成、编辑或审查前, 应读取该 skill 的 `references/style.md`。
- Python 格式化和 lint 优先使用 Ruff, 并在环境允许时使用该 skill 提供的 Ruff 脚本。
- 代码修改应保持行为不变, 不为了风格偏好引入无关重构。
- 若项目已有约定与 skill 冲突, 应先说明冲突, 默认优先项目现有约定。
- 注释和 docstring 应解释意图、职责和流程, 避免描述显而易见的代码动作。

## 非目标

- 不重写 `freeplot` 的核心绘图 API。
- 不主动改变现有图形输出风格。
- 不进行大规模功能扩展。
- 不直接发布 PyPI。
- 不引入复杂文档站点主题或 CI 流程, 除非后续计划明确需要。
- 不为所有绘图功能补齐完整测试矩阵, 本阶段只建立最小可维护验证基础。
- 不维护独立 demo 目录作为主要交付物, 示例以 `docs/` 文档内容为准。

## 约束

- 优先使用成熟方案, 避免自定义复杂工具链。
- 参考 `freerec` 的工程形态, 但要适配 `freeplot` 的可视化库定位。
- 代码注释使用英文。
- 代码风格规整应遵循 `format-code-style` skill, 并优先保持项目现有约定。
- 文档文字保持简练直白。
- 已确认的验证标准不得因实现便利被随意弱化、删除或绕过。
- 修改应尽量小步推进, 避免无关重构。

## 用户场景

- 新用户可以通过 README 快速了解 `freeplot` 的定位、安装方式和基本用法。
- 使用者可以通过示例快速找到常见图形的绘制方式。
- 维护者可以通过测试和 lint 快速判断改动是否破坏基础行为。
- 文档读者可以在本地构建文档并浏览安装、快速开始、示例和 API 入口。

## 输入与输出

### 输入

- 当前 `freeplot` 项目代码、README、示例和图片资源。
- `freerec` 项目作为工程结构和文档组织参考。
- `format-code-style` skill 作为代码风格、注释、类型标注、Ruff 和测试组织参考。

### 输出

- 更新后的项目规整方案。
- 新增或更新的构建配置、文档目录、测试目录和开发配置。
- 整理后的 README、示例说明和文档入口。
- 可执行的本地验证方式。
- 与 `format-code-style` skill 对齐的代码风格规整结果。

## 边界条件

- 若部分示例依赖交互式后端, 应调整为可保存图像或可在无 GUI 环境中跳过交互。
- 不需要优先考虑旧版本兼容性, 技术方案可选择更现代的 Python 与工具链基线。
- 若 README 中现有图片路径与 docs 构建路径冲突, 应统一资源引用策略。
- 若 `setup.py` 与 `pyproject.toml` 同时存在, 应避免项目元数据长期不一致。

## 异常与失败场景

- 本地安装失败。
- 包导入失败。
- 文档示例执行失败或阻塞。
- 文档构建失败。
- 测试依赖缺失或版本不兼容。
- 示例目录合并后路径引用失效。

## 验收标准

- `pip install -e .` 可成功安装项目。
- `python -c "import freeplot"` 可成功执行。
- `pytest` 可通过最小测试集合。
- Ruff 检查或格式化流程可执行, 或对无法执行的原因给出明确说明。
- 核心文档示例可在无 GUI 环境下运行或被明确标记为需要人工验证。
- 文档可本地构建, 且至少包含安装、快速开始、示例和 API 入口。
- README 与 docs 的安装方式、项目定位和核心示例描述一致。
- 项目结构清晰, 重复 demo 目录不再作为主要学习入口。

## 未决问题

- Python 版本要求不需要考虑旧版本兼容性, 推荐在计划中选择现代基线。
- 文档语言采用中文、英文, 还是中英文双语。
- 是否在本阶段引入 GitHub Actions CI。
- 是否完全移除 `setup.py`, 或在过渡期保留。
- 是否删除现有 `demos/` 和 `freeplot/demos/`, 或仅停止将其作为文档入口。
